Overview

This is the Nepal Bipolar Foundation web application — an admin dashboard for managing members of a foundation supporting people living with bipolar disorder in Nepal. It is a full-stack project with three parts:

  • Backend — server/: Feathers 5 + Express + Mongoose API. Handles login (JWT), user registration, profile updates, image uploads, and serves the built frontend in production.
  • Frontend — client/: Vue 3 + Vite + Pinia single-page app. Login/register screens plus a dashboard with a Users table (full CRUD) and a Profile page.
  • Orchestration — Root-level dev.mjs, docker-compose.yml, Dockerfile, and package.json glue the two halves together.

Key design decision

User records are split across two collections: users holds identity + login data (name, email, hashed password, avatar), while user_details holds optional profile info (age, city). Feathers hooks keep the two in sync so the API looks unchanged to the client — a nice example of normalizing data behind the API layer.

Request flow example — login:
1. Login.vue submits email + password.
2. The Pinia auth store calls feathers.authenticate() → POST /authentication.
3. Server verifies against the users collection via the local strategy and returns a JWT.
4. The JWT is stored in localStorage; auth.user is filled → App.vue swaps to the Dashboard.
5. Every later request (e.g. GET /users) sends the JWT, verified by the jwt strategy.

Root-level files

./package.json npm workspace entry point

The top-level npm manifest. It holds no dependencies itself — it exists to give the whole repo a name and three convenience scripts:

  • dev / start → run node dev.mjs (launches server + client together).
  • typecheck → runs npm run typecheck --prefix server then --prefix client, i.e. type-checks both halves from one command.

It is the file the Dockerfile's npm start and local npm run dev both hang off.

./dev.mjs local orchestrator

A small Node script that runs the API and the Vue dev server simultaneously, so one command starts the whole stack.

  • spawn() launches npm run dev in server/ and client/.
  • Each child's stdout/stderr is line-prefixed with [server] / [client] so the output stays readable.
  • Windows handling: npm is npm.cmd on Windows, so children run through cmd.exe /c; on macOS/Linux they run npm directly.
  • Clean shutdown: on Ctrl+C it runs taskkill /pid <pid> /T /F on Windows (npm spawns grandchildren like tsx/vite that must be killed too) or SIGTERM elsewhere, then exits.

./docker-compose.yml one-command Docker stack

Declares the two containers that make up the production stack:

  • mongo — official mongo:7 image. Its data is persisted in a named volume mongo-data mapped to /data/db, so it survives docker compose down.
  • app — built from the Dockerfile. It depends_on mongo and receives the MONGODB_URI=mongodb://mongo:27017/nepal-bipolar-foundation env var. The mongo hostname is resolved by Docker's internal DNS to the database container. Port 3030 is exposed to the host.
Both containers use restart: unless-stopped, so they come back after crashes or machine reboots.

./Dockerfile multi-stage production build

Builds the entire app into a single image using three stages so the final image stays small:

  1. client-build (node:20-alpine): installs client deps with npm ci --legacy-peer-deps and runs vite build → static files in /app/client/dist. An empty VITE_SERVER_URL is baked in so the SPA talks to the API on the same origin (localhost:3030).
  2. server-deps (node:20-alpine): installs server deps (again with --legacy-peer-deps) into /app/server/node_modules.
  3. runtime (node:20-alpine): copies the server's node_modules and source, then copies the built client into /app/public/app and sets CLIENT_DIST to point at it. Exposes port 3030 and runs npm start (the Feathers API, which also serves the frontend).

COPY client/package.json client/package-lock.json ./ before copying the rest is a cache-friendly trick: dependency layers only rebuild when the lockfile changes.

./.dockerignore build context exclusions

Tells Docker what not to send into the build context, keeping the build fast and the image clean:

  • **/node_modules — reinstalled fresh inside the (Linux) container; Windows copies would be broken and useless.
  • **/dist — regenerated during the Docker build.
  • .git, *.log, README.md — not needed in the image.

server/config/default.json runtime configuration

Read by the configuration() plugin and accessed via app.get('port'), app.get('mongodb'), etc.

  • port: 3030 — API port.
  • mongodb — local connection string; overridden by the MONGODB_URI env var (Docker).
  • authentication — JWT settings: 1-day expiry, HS256, audience https://nepalbipolarfoundation.org, and the local strategy using email/password fields.
⚠️ Security: secret is "CHANGE-ME-to-a-long-random-string". In production this must be replaced with a long random string.

server/src/index.ts server entry point

The file Node executes first. It:

  1. Imports the configured Feathers app from app.ts.
  2. Reads the port from config.
  3. Connects to MongoDB (process.env.MONGODB_URI || app.get('mongodb')). If MongoDB is down, it prints a clear error and calls process.exit(1).
  4. Calls app.listen(port) and logs readiness.

Everything is wrapped in an async start() so the sequence reads top-to-bottom.

server/src/app.ts the heart of the server

Assembles the Feathers app (which is an Express app). Order matters:

  1. configuration() — loads default.json.
  2. cors() — lets the browser app on port 5173 call the API.
  3. json() + urlencoded() — body parsers.
  4. serveStatic('/public') — exposes uploaded images.
  5. rest() — enables REST transport for services.
  6. upload — the multer route.
  7. users then userDetails — the two Feathers services.
  8. serveStatic(clientDist) — serves the built Vue app in production (env CLIENT_DIST or client/dist).
  9. authentication — after the users service because it adds security hooks to it.
  10. notFound() + errorHandler() — 404s and friendly JSON errors last.

server/src/authentication.ts login & JWT security

  • Creates an AuthenticationService exposed at POST /authentication.
  • Registers two strategies:
    • local — proves identity with email + password.
    • jwt — proves identity with an existing token (for later requests).
  • Attaches security hooks to the users service:
    • hashPassword('password') on create — bcrypt before saving.
    • authenticate('jwt') on find/get/patch/update/remove — every read/write after registration requires a token.
    • protect('password') on all (after) — the hash is stripped from every external response.

server/src/types.ts shared server types

  • Configuration — the shape of config/default.json, so app.get('port') is typed as number.
  • ServiceTypes — the registry of services (users, user-details, authentication). users/user-details are typed any because feathers-mongoose doesn't ship types yet.
  • Application — ExpressFeathers<ServiceTypes, Configuration>, the fully typed app used across the codebase.

server/src/upload.ts profile image uploads

A plain Express route (not a Feathers service — totally fine, they mix freely).

  • Uses multer with diskStorage, saving into server/public/uploads/ (created recursively on first use).
  • Filenames are unique: avatar-<timestamp>-<random>.<ext>, so two users can't overwrite each other.
  • Only safe image extensions are kept (.jpg/.jpeg/.png/.gif/.webp); anything else falls back to .jpg.
  • Limits: one file, 2 MB max, MIME must start with image/.
  • On success it returns { url: "http://host/public/uploads/avatar-...jpg" }, which the client stores on the user record.

server/src/services/users/ the /users service

users.types.ts

The User TypeScript interface. Note it includes age and city even though they aren't stored on the document — hooks re-attach them so the API shape is stable.

users.model.ts

The Mongoose schema: name (required), email (required, unique index, lowercase+trimmed — the login username), password (required, stored hashed), avatar (nullable string). Timestamps enabled. Collection name: users.

users.service.ts

Makes users a Feathers service (auto REST endpoints) and implements the two-collection sync:

  • extractDetails (before create/patch) — if age or city was sent, pull it out of the user data and stash it on context.params._userDetails.
  • saveDetails (after create/patch) — writes/updates the row in user_details (creates it on first registration).
  • attachDetails (after find/get/patch) — reads the details row back and adds age/city to every returned user, so responses look unchanged.
  • removeDetails (after remove) — deletes the details row so no orphans remain.

There's also a small runtime type-cast for feathers-mongoose (a CommonJS package whose shipped types describe the default differently than reality).

server/src/services/user-details/ the /user-details service

user-details.types.ts

The UserDetails interface: userId (an ObjectId back to users), nullable age and city, plus timestamps.

user-details.model.ts

Schema with a unique userId index (one details row per user), explicit collection name user_details, timestamps on.

user-details.service.ts

Exposes the collection as a Feathers service and locks every method down with authenticate('jwt'). The client never calls it directly — the /users hooks are its only real consumer. (Internal hook calls have no provider, so they bypass the auth hook.)

client/src/feathers.ts the shared API client

The single place that talks to the server from the browser:

  • Defines the User interface and typed ServiceTypes, so feathers.service('users').create(...) is fully type-checked.
  • SERVER_URL = import.meta.env.VITE_SERVER_URL ?? 'http://localhost:3030' — dev points at the API; in the Docker build the env var is empty so the SPA calls its own origin.
  • Configures the REST client. Note the fetch(url, init) => fetch(url, init) wrapper: the browser requires fetch to be invoked with window as this, otherwise it throws "Illegal invocation".
  • Enables authentication with localStorage as storage — the JWT survives page refreshes.

client/src/App.vue root component / page switcher

Reads auth.isAuthenticated from the Pinia store:

  • Not logged in → a centered brand header plus either Login.vue or Register.vue (switched by a local showRegister ref fed by the go-register/go-login events).
  • Logged in → Dashboard.vue.

On mount it calls auth.restore() to validate any saved JWT and pre-fill the session. Because the store is reactive, the whole screen swap happens automatically when auth.user changes — no router is needed. Also holds the global stylesheet (body background, fonts, green brand color).

client/src/stores/auth.ts Pinia auth store

The single source of truth for the logged-in user:

  • state — user (User | null).
  • getters — isAuthenticated (true when user !== null).
  • actions:
    • restore() — calls feathers.reAuthenticate() to validate a saved JWT and fill user; on failure stays logged out.
    • login(email, password) — feathers.authenticate({ strategy: 'local', ... }) then stores the user.
    • logout() — clears the token and user.
    • updateUser(user) — refreshes the stored user after a profile save.
Because the store is reactive, changing user here re-renders every component that reads it — App.vue, Dashboard, Profile.

client/src/components/Login.vue login form

A simple email/password form bound with v-model (email is trimmed + lowercased before sending). On submit it calls auth.login(...); success fills auth.user and App.vue auto-switches to the Dashboard — nothing needs to be emitted up. Errors are shown in reserved space so the layout doesn't jump; the button is disabled while loading. The only event is go-register to switch screens.

client/src/components/Register.vue registration form

Registration with an optional profile photo. On submit:

  1. Client-side validation — required fields, password ≥ 6 chars, password & confirm must match.
  2. Upload (if a file was picked) — sends FormData with field image to POST {SERVER_URL}/upload and gets back the public URL. A live preview shows the chosen image first.
  3. Create — feathers.service('users').create({ name, email, password, avatar }). The server hashes the password.
  4. Auto-login — calls auth.login(...), which drops the user straight onto the Dashboard.

Duplicate emails are caught by looking for a 409 status or a "duplicate" message and showing a friendly hint.

client/src/components/Dashboard.vue logged-in shell

Two-panel layout: a dark-green sidebar (title, menu buttons Users and Profile, red Log out button) and a main content area that swaps between the selected component based on a local activeMenu ref. Logout simply calls auth.logout(), which empties the store and pops the UI back to the login screen.

client/src/components/UsersAdmin.vue user CRUD page

The biggest component. Full CRUD over the users service:

  • Read — loadUsers() calls users.find() (GET /users) on mount and renders a table (avatar thumbnail or initials, name, email, age, city, join date, actions).
  • Create — "Add user" opens a modal form → users.create().
  • Update — "Edit" opens the same modal prefilled (email is locked when editing because it's the login username) → users.patch(id, {...}). Age is parsed to a number or null; only a new password is required on create.
  • Delete — "Delete" asks for window.confirm() then calls users.remove(id).

After every mutation it reloads the table and shows a status message; duplicate-email errors map to a friendly hint.

client/src/components/Profile.vue profile page

Shows the logged-in user's photo (or initials placeholder), name, and read-only email. The user can:

  • Change their photo — upload to /upload then users.patch(id, { avatar }).
  • Change their name — users.patch(id, { name }).
  • Log out.

Only changed fields are sent. After a successful save it calls auth.updateUser(updated) so every screen reflects the new data, then shows "Profile saved."

client/src/vite-env.d.ts Vite ambient types

A one-liner that references Vite's client types, giving you typed access to import.meta.env (used for VITE_SERVER_URL) and CSS imports.

Key takeaways

  • One command to run: npm run dev locally or docker compose up --build for the full stack.
  • Feathers powers everything: services auto-become REST endpoints, hooks handle security and the two-collection sync, and the same client library mirrors the server in the browser.
  • Passwords are never stored or returned in plain text — hashPassword and protect hooks enforce it server-side.
  • The data model is normalized behind the API: users + user_details, kept in sync by the users service hooks.
  • Dev vs. prod: Vite serves the client in dev (port 5173, CORS to 3030); in the Docker image the Feathers server serves the built SPA from the same origin (3030).
